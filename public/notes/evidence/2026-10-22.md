## 协议与数字口径

### 排队模型

- 输入为均匀到达：第 i 个任务在 i×1.5 秒到达，i=0..399。每项耗时固定 20 秒；分别使用 4、8、16 个相互独立的执行槽；无重试，无有限队列拒绝，无资源争用。
- 第 600 秒的统计约定：finish ≤ 600 算完成，start ≤ 600 < finish 算处理中，start > 600 算等待。
- P95 是全部 400 项的最终开始时间减到达时间，采用最近秩 ceil(0.95×400)，不是窗口内完成任务的截尾统计。
- 4/8/16 槽的等待数分别 279/159/0；完成数 117/233/387；处理中 4/8/13。4 槽最后完成于 2004.5 秒，8 槽 1010.5 秒，16 槽 618.5 秒。
- 外部额度 300 次/分钟、每视频 10 次也是假设，只计算 30 视频/分钟上限，没有模拟第三方服务。

### 双连接模型

- owner=alice/bob 是测试指定的可信主体，不是实际登录。只按 ID 查询可读到 Alice 记录，附加 owner=bob 后无结果；owner=alice 正常可读。
- 两连接先读同一个值，再各写 value+1：两次独立 SQL 更新后最终只有 1。
- version 条件写入：影响行数依次为 1、0、重读后 1，最终值 2。
- 当前 epoch=2，旧 epoch=1 的结果提交影响 0 行，epoch=2 影响 1 行。只验证提交谓词；不测试领取、续租、到期时钟、网络故障或外部副作用。

### 检索演示

- 四组候选排名是人工设定的反例，未从关键词或向量引擎生成。A-M 是示例文档标识，并无真实语料与模型推理。
- RRF 常数 c=60，rank 从 1 开始，文档 ID 去重，同分按 ID 排序，截断 K=3。
- 每题一个相关项；Recall@3 是相关项找回比例，MRR@3 是截断倒数排名的均值，Hit@1 是首项相关比例。
- 关键词、向量的 MRR@3 均为 5/12，RRF 为 1/3。所有方案 Recall@3 均为 3/4。
- oracle 明确访问 gold，只把已有候选里的相关项提到最前，MRR@3=3/4。它是诊断上界，绝不是实际重排收益；第四题的 J 没进入候选，不能被补进结果。
- 不计算显著性、生产质量或服务延迟。脚本耗时不是检索延迟。

## 静态检索边界

- 在 `myclaw/gateway/server.py` 中检索 `resolve_gateway_subject` / `require_subject_access` 未发现调用；上面的入口摘录显示请求参数与固定 sender_id。这个结论限于所检查版本，不代表已审计代理、网络部署或其他产品的认证层。
- 在 DOVideo-AI 的 Java 源码中检索 `aiTaskExecutor` / `@Async`，配置之外的显式使用位于 `TranscriptionTaskService`。因此容量正文没有把这个 Bean 的最大线程数当作视频分析消费者并发。
- 没有在参考项目中定位到可用于本次真实对照实验的 RRF/重排实现；检索篇明确采用独立算法演示。
